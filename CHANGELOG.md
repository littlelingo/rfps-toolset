# Changelog

## Unreleased

- **RFI profile (first pass)**: `solicitation_type = "rfp" | "rfi"` in `solution.toml` (`rfps-new-engagement --type`, `rfps-set-config solicitation_type`). For an RFI the steps marked `rfi_optional` in `flow.toml` (resources, attachments) are optional and hidden until they need attention. The mapper, drafter, validator and start skills say what differs for an RFI (questions as rows, non-binding wording, responsiveness check). New smoke checks and an `rfi-start-fires` eval. `rfps-sweep` scopes to the respondent's asks for an RFI (`sweep_scope`, `sweep_files`): on the IRS MIDS RFI that is 12 asks instead of 325 obligation sentences, most of them the draft PWS. Not yet built: RFI section templates, a commitment-language lint, a proprietary legend, a response-deadline countdown, an RFI fixture.

## 0.7.0 (2026-11-02)

- **Master Google Doc for the WIP**: the shared WIP now starts from a copy of a styled, blank master Google Doc that meets a style profile (the standard, `tools/templates/styles`), so it carries real named styles, header, footer and cover-page rule instead of a rebuild from the Word template. The master is made as a native Google Doc from the profile (`--master-plan`, two direct-edit sends; the profile's fonts and colors are applied as direct formatting because the Docs API cannot change named styles), as a Word file converted by Google (`--master-docx`), or cleaned from any conforming doc; no one finished response is the reference. `--set-default-master` records a shared master in the profile file. Drift is guarded in four places: with no master (the default) `/rfps:build-wip` makes a fresh doc from the profile for each solution, so there is nothing shared to drift; a registered master carries the profile's fingerprint and `--template-id` refuses a stale one (exit 3); `--wip-check` compares the WIP's real formatting with the profile; and `rfps-final-gate` checks the PDF's fonts against the profile (`[final_gate] fonts` lists an RFP-required exception). New in `rfps-sync-gdoc`: `--template-check` (compare a master with a style profile), `--clean-plan` (empty a copy of a finished response, keeping styles, header and footer), `--skeleton-plan` (write the response template's headings, evaluation lines and placeholders into the blank copy in the master's styles), `--template-id` (refuses when no master is registered), and `--set-template <link> --profile <name>`. The first profile is `formal` (`tools/templates/styles/formal.toml`). `/rfps:build-wip` stops without a master unless `--plain` is passed. Not built: the Google FINAL route (item 3.0), a `whitepaper` profile.

## 0.6.0 (2026-10-31)

Checks and content that make the proposal stronger and the compliance harder to miss, kept out of the way: the flow stays the same, and optional steps stay hidden until they need attention.

- **Obligation sweep** (`rfps-sweep`, `/rfps:sweep`): every sentence in the solicitation that obliges the bidder (shall, must, may not, change verbs) is compared with the requirement rows, and sentences with no row are listed. Quoted text in rows is verified against the source. Extracted text is kept in `.state/text/` between runs and re-read when a source file changes.
- **Living documents with stable IDs**: `capture.md` (bid decision, `/rfps:capture`), `win-strategy.md` (factors, themes, exhibits, `/rfps:win-strategy`), `evaluation-sim.md` (scores the response as an evaluator would, with per-file staleness, `/rfps:evaluator-simulator`), `submission.md` (`/rfps:submission`), `questions.md` (`/rfps:questions`), `/rfps:orals` and `/rfps:debrief`. `/rfps:start` proposes these as starting points, never records an answer the user did not give, and ends with a lean hand-over.
- **Deterministic checks in `rfps-refresh-reports`**: writing lint (`rfps-lint`: superlatives, passive voice, we-ratio, acronyms, duplicates, hedges; tunable under `[lint]`), cross-reference of requirement to section (`rfps-crossref`), consistency of figures inside the response, against the solicitation and across sections (`rfps-consistency`; reads percents, direction of limits, amendment-replaced figures), price view and rate-sheet checks, exhibit plan and page budget, past-performance thresholds (`[past_performance]`), approval proof (`require_approval_ref`, off by default), and a check that living tables are well formed. Autochecks are listed worst first with a count line.
- **Structured evidence**: the register has nine more columns (`rfps-register-add --update`); registers saved by Excel with a byte-order mark are read correctly.
- **Final gate** (`rfps-final-gate`, `/rfps:final-gate`): checks the PDF exported from Google Docs (page count, internal markers, links to Docs, author metadata, required wording across line wraps, sparse and empty pages) and `--scrub` removes metadata. No LibreOffice is needed.
- **Writing help**: six more section templates (executive summary, management plan, transition, risk register, quality assurance, schedule).
- **Flow**: `flow.toml` has five optional steps (bid, questions, strategy, evaluation simulation, debrief) shown only when they need attention; `rfps-worklist` ranks amendment-not-applied, weak evaluator factors, overdue submission steps and open questions.
- **Fixes**: settings written by `rfps-set-config` and `rfps-sync-gdoc` stay above the first table in `solution.toml`; second-reader staleness no longer clears itself on a refresh; free-text statuses such as "Yes - section 3.2" count as done; the sweep and cross-section comparison are fast on large solicitations; the price view no longer treats counts and page limits as ceilings; malformed table rows are reported, not dropped.
- 13 new eval cases (obligation and validator checks, drafter markers, routing for each new skill).
- Not yet built: an automated Google Docs route for the final copy (use File > Download > PDF from a clean copy).

## 0.5.0 (2026-10-30)

- Teamwork: `/rfps:start` is the single entry point and begins with an entry check (`references/entry.md`): no solution means start, an existing solution means join (never overwritten); new `rfps-collab`. Joining records your name (local), checks `cache_dir`, and briefs you on who is writing, claimed worklist items (now `mine by <name>`), recent changes and duplicate IDs. Write commands take a short lease (`.state/lease.json`); `rfps-register-add` re-reads the register before writing so simultaneous adds do not share an ID.

- `[GROUNDED]` markers get a green circle icon like the other markers (`rfps-open-items --mark`); it is for scanning only and GROUNDED never appears in the open items.
- Deep folders: `rfps-scan-sources` reports how many files and folders it looked at and how deep, names file types it could not read and files that gave no text; a Drive listing now covers every subfolder (`path`, `listed`), flags subfolders not yet listed and shortcuts to resolve, and the digest names Drive files by path.
- New `rfps-set-config`: `wip_folder` (Drive folder for the shared WIP and template copy), `wip_docx`, `final_copy_dir` and `cache_dir` (a folder on this machine for text caches and scratch builds, refused inside Drive). `/rfps:start`, `/rfps:build-wip` and `/rfps:build-final` ask for these locations and use the defaults (`05 Draft Response`, `11 Final Submission`, never the Drive root) only when none is given.
- Drive for Desktop: the scan lists Google-format pointer files (`.gdoc`, `.gsheet`, `.gslides`) for the connector route, and says when a Drive mount is offline; `rfps-scan-sources --text-dir` prints where text is kept; README section "Working With Google Drive".
- The Drive tree is summarized and confirmed once before reading.
- New `rfps-decode-b64` decodes a Drive download that the app saved to a file into a real .docx/.xlsx/.pdf; skills now say never to retype base64 by hand and to ask the user to download the file when only the chat has it.

## 0.4.1 (2026-10-25)

- **The status pane no longer opens by itself.** It used to open at every session start, in every project, and run `rfps-status-page --json` once a minute whether or not the session had anything to do with an RFP. Now a session start only registers `/rfps-pane` and `/rfps-status-pane`; opening the pane (and its first status read, and the once-a-minute refresh that follows) happens only when someone asks for it. The refresh timer is started once however often the pane is opened. A test checks that a session start opens nothing and runs nothing, and the state it needed (`rfps.watching`) is declared in `types/`. The status page (`/rfps:status-page`) was never automatic.

## 0.4.0 (2026-10-24)

- One collector, several views: `open-items.md` and the status page show the choice recorded on each marker (`(mine)`, `(skipped)`), and `rfps-worklist --set` also takes a flow step id (done, skip, reset in `progress.md`). No new tracking files.

- New `/rfps:start`: a front-loaded run. It asks once for the solicitation folder, template, past-performance locations and the WIP format, then sets up, analyzes, maps requirements, proposes evidence rows (as `hold`, never `cleared`), plans staffing, drafts, reviews and builds the first shared WIP document, then hands over a worklist.

## 0.3.0 (2026-10-24)

- **The Google Doc now starts as a copy of a Google version of the Word template.** `/rfps:make-gdoc-template` builds that Google Doc once from the Word template: `--html` now carries the template's cover text, form tables, boilerplate and evaluation lines (not just headings), and `--style-plan` reads the Word template's page size, margins, fonts, sizes, colors, line spacing, header and footer and writes them as direct formatting (the header and footer through `createHeader`/`createFooter`; page-number fields cannot be added through the connector). `rfps-sync-gdoc --set-template` records it as `gdoc_template` in `solution.toml`; `/rfps:build-wip` copies it with Drive `copy_file`, which keeps headers, margins and fonts. `--init` now refuses a doc whose headings differ from `response/` (`--allow-mismatch` overrides), and treats any non-placeholder text under a heading (boilerplate, forms) as the template's: it is never replaced, and the response text is inserted after it. `rfps-update-template --doc FILE` compares a Google Doc's headings. A `read_doc` file saved by the connector (wrapped in `content`) is read as is. Verified live on a test template (copy, formatting, header and footer, suggestions after the boilerplate, a table and bullets); the second bullet came back as a plain paragraph in the live read and needs a look.
- **Template generation and `/rfps:update-template`:** `/rfps:generate-template` reads the solicitation (base and amendments) for how the response must be organized, proposes a section outline with a source citation for each section, and after approval `rfps-make-template` writes `05 Draft Response/Response Template.docx` (Heading 1-3, a Subtitle line for what the section must show, a `[text]` placeholder; never overwrites). `/rfps:update-template` (`rfps-update-template`) compares a changed template's headings with `response/`: new sections are added empty in order, renames are applied on request (`--rename` for close matches, `--rename-all` for same-place rewordings a person confirms), removed headings are only reported, and nothing is deleted.

## 0.2.0 (2026-10-24)

- **`/rfps:add-past-performance` grew up:** several locations in one call (`rfps-add-source a b c`), a scan for new and changed files (`rfps-scan-sources`: extracts text for what changed, skips the rest, writes `past-performance/digest.md` with the years, amounts and permission wording each file mentions), a Google Drive folder as a source (Claude lists it through the connector, `rfps-scan-sources --drive LABEL --listing/--ingest` compare and record it, and nothing is read until the user confirms), and `rfps-register-add`, which assigns the next free evidence ID and refuses `cleared` unless the user's own confirmation is passed (`--confirm-cleared`). The skill now proposes rows for approval and defaults every row to `hold`.
- CI (`.github/workflows/ci.yml`: lint, the smoke test with its Word and Google routes, and plugin validation) and `ruff.toml` (errors and unused names only). Removed the unused imports and variables the lint found. `rfps-extract-docs` also reads `.txt` and `.md`.

- **Google Docs is now the default shared WIP document** (`wip_format = "gdoc"`; `--word` or `wip_format = "docx"` keeps the Word route). `rfps-sync-gdoc` plans everything and Claude reads and writes the doc through the Google connectors: `--html` builds the first version for Drive `create_file`, `--init` records it, `--push` writes the `update_doc` requests as *suggestions* (only the changed words, bullets and tables inserted in place, highest index first, guarded by the revision), `--commit` records the sync, `--pull` lists edits others made (and `--comments` writes their comments to `review/doc-comments.md`). Open items link to the Google Docs heading. Tested against a simulated Docs API (`fixtures/gdoc_sim.py`, `fixtures/gdoc_test.py`) and once against live Google (2026-10-23): Drive converted the generated HTML cleanly; `update_doc` accepted `writeMode: SUGGEST` and the word edits, new bullet and new paragraph came back as real suggestions that parse back as in sync; a direct edit was pulled into the response. Not yet live-tested: comments (the connector has no way to create one and none were present), tables inserted as suggestions, the optional Subtitle styling. Google's `read_doc` returned no `headingId` for the converted headings, so open items link to the doc with the text to search for, not to the heading.
- **Comments and jump-to-spot (Google Docs):** Claude adds a comment anchored on each open `[DECISION]`, `[OPEN]` and `[EVIDENCE NEEDED]` marker (`rfps-sync-gdoc --comments-plan`, `--comments-commit`; the connector's `update_doc` accepts `insertComment` but has no reply or resolve request). Every comment in the doc, ours and people's, is tracked in `.state/gdoc-comments.json` and `review/doc-comments.md`, with new comments, new replies, resolved and deleted comments reported on each pull, plus two cross-checks against the response (comment still open after its marker left; comment resolved while the marker remains). Open items link to their comment (`?disco=<comment id>`, adjustable with `gdoc_comment_link` in `solution.toml`; the exact link format still needs checking in a browser), else to the doc. `rfps-sync-gdoc --comment-note` records how a comment was handled.
- **Indicators in the Google Doc:** markers are colored by a direct formatting pass (`--highlight-plan`: green GROUNDED, yellow ASSERTION, red DECISION, orange OPEN, purple EVIDENCE NEEDED; formatting only, so not a suggestion per marker). Comments are added for DECISION, OPEN and EVIDENCE NEEDED markers, and also for response changes skipped because the text was edited in the doc (CONFLICT, with the response wording), evidence that is not cleared or missing (EVIDENCE) and banned phrases (BANNED); assertions get none unless `--kinds` asks. A comment follows its marker if the marker is reworded. `--pull --promote` turns a reviewer's open comment into an `[OPEN]` marker (with approval). The pull and `--status` report how many suggestions and comments are waiting for people, and a new flow step, "Suggestions and comments in the shared document settled", tracks them before FINAL. Fixed: a tag followed by punctuation (`[GROUNDED: E-002].`) was not found.
- **Every addition to the Google Doc is a suggestion, including the first draft:** the new doc holds only the template's headings, evaluation lines and placeholders (`--html` is a skeleton), and `--push` always uses `writeMode: SUGGEST`. The `--direct` option and the direct Subtitle styling step are gone.
- `/rfps:pull-docx` is now `/rfps:pull-wip` and handles both routes.
- Shared WIP docx: `/rfps:build-wip` now creates one WIP docx in `05 Draft Response` and updates it in place with `rfps-sync-docx`. Approved response changes go in as tracked changes (author "rfps"), only for paragraphs whose text changed, so other people's comments and edits are kept; a response change that touches text someone edited in the document is reported and left pending. `--status` shows drift, `--dry-run` previews, `--rebuild` regenerates (with a backup). `rfps-build-response --mode wip` remains the stateless regeneration into `build/`.
- `/rfps:pull-wip` (`rfps-sync-docx --pull`): lists edits others made in the shared WIP docx that the response lacks (changed words, new and deleted paragraphs, tables, removed markers) and writes their comments to `review/doc-comments.md`; after approval `--pull --apply` writes them into `response/*.md`, keeping bold and tags on unchanged words. Changes both sides touched are reported as conflicts. The flow's WIP step now shows whether the document or the response is ahead.
- Locators: open items (`open-items.md`, the status page and the pane) link to the shared WIP docx section and show the marker text to search for, once the document exists (`open_in = "docx"|"md"` in `solution.toml` overrides). `rfps-sync-docx` adds an invisible bookmark to every heading, including in existing documents. `rfps-open-doc` opens the document and copies the search text; Word cannot be driven to an exact spot from outside, so use its Navigation Pane for the heading.
- `tools/sync_core.py` plans changes from block texts, separate from the docx backend, so a Google Docs backend can be added later.
- `/rfps:build-final` checks for edits made in the shared document before building.
