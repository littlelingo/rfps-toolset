# Changelog

## 0.3.1 (2026-10-24)

- Best-practice audit follow-ups: `integrate`, `resources`, `status`, `next` and `step` are typed-only shortcuts (the `integrate-edits`, `resource-planner` and `solution-guide` skills keep the plain-wording entry, so there is one natural-language route for each and a smaller always-on listing); standard `rfps--vX.Y.Z` tags for 0.1.1, 0.2.0 and 0.3.0 (the older `vX.Y.Z` tags stay), `claude plugin tag --push` for later releases; a release checklist in CONTRIBUTING; a new eval case for marking a step done in plain words. The directory-listing fields (icon, support and privacy URLs) are left unset until the repository is public and a directory submission is planned.
- Followed the plugin best-practice checklist: `build-wip`, `build-final`, `make-gdoc-template` and `new-engagement` are now `disable-model-invocation: true` (typed only; they create files, documents or submission copies); added an `evals/` suite for `claude plugin eval` (collateral analyzer, requirements mapper and solution guide fire on plain wording; an unrelated request stays quiet; drafting without evidence flags gaps; clearance is never granted by the tool; the template outline cites the RFP); and a "What This Plugin Runs" section in the README (components, what each runs and where, Claude Code only).

## 0.3.0 (2026-10-24)

- **The Google Doc now starts as a copy of a Google version of the Word template.** `/rfps:make-gdoc-template` builds that Google Doc once from the Word template: `--html` now carries the template's cover text, form tables, boilerplate and evaluation lines (not just headings), and `--style-plan` reads the Word template's page size, margins, fonts, sizes, colors, line spacing, header and footer and writes them as direct formatting (the header and footer through `createHeader`/`createFooter`; page-number fields cannot be added through the connector). `rfps-sync-gdoc --set-template` records it as `gdoc_template` in `solution.toml`; `/rfps:build-wip` copies it with Drive `copy_file`, which keeps headers, margins and fonts. `--init` now refuses a doc whose headings differ from `response/` (`--allow-mismatch` overrides), and treats any non-placeholder text under a heading (boilerplate, forms) as the template's: it is never replaced, and the response text is inserted after it. `rfps-update-template --doc FILE` compares a Google Doc's headings. A `read_doc` file saved by the connector (wrapped in `content`) is read as is. Verified live on a test template (copy, formatting, header and footer, suggestions after the boilerplate, a table and bullets); the second bullet came back as a plain paragraph in the live read and needs a look.
- **Template generation and `/rfps:update-template`:** `/rfps:generate-template` reads the solicitation (base and amendments) for how the response must be organized, proposes a section outline with a source citation for each section, and after approval `rfps-make-template` writes `05 Draft Response/Response Template.docx` (Heading 1-3, a Subtitle line for what the section must show, a `[text]` placeholder; never overwrites). `/rfps:update-template` (`rfps-update-template`) compares a changed template's headings with `response/`: new sections are added empty in order, renames are applied on request (`--rename` for close matches, `--rename-all` for same-place rewordings a person confirms), removed headings are only reported, and nothing is deleted.

## 0.2.0 (2026-10-24)

- **`/rfps:add-past-performance` grew up:** several locations in one call (`rfps-add-source a b c`), a scan for new and changed files (`rfps-scan-sources`: extracts text for what changed, skips the rest, writes `past-performance/digest.md` with the years, amounts and permission wording each file mentions), a Google Drive folder as a source (Claude lists it through the connector, `rfps-scan-sources --drive LABEL --listing/--ingest` compare and record it, and nothing is read until the user confirms), and `rfps-register-add`, which assigns the next free evidence ID and refuses `cleared` unless the user's own confirmation is passed (`--confirm-cleared`). The skill now proposes rows for approval and defaults every row to `hold`.
- CI (`.github/workflows/ci.yml`: lint, the smoke test with its Word and Google routes, and plugin validation) and `ruff.toml` (errors and unused names only). Removed the unused imports and variables the lint found. `rfps-extract-docs` also reads `.txt` and `.md`.

- **Google Docs is now the default shared WIP document** (`wip_format = "gdoc"`; `--word` or `wip_format = "docx"` keeps the Word route). `rfps-sync-gdoc` plans everything and Claude reads and writes the doc through the Google connectors: `--html` builds the first version for Drive `create_file`, `--init` records it, `--push` writes the `update_doc` requests as *suggestions* (only the changed words, bullets and tables inserted in place, highest index first, guarded by the revision), `--commit` records the sync, `--pull` lists edits others made (and `--comments` writes their comments to `review/doc-comments.md`). Open items link to the Google Docs heading. Tested against a simulated Docs API (`fixtures/gdoc_sim.py`, `fixtures/gdoc_test.py`) and once against live Google (2026-10-23): Drive converted the generated HTML cleanly; `update_doc` accepted `writeMode: SUGGEST` and the word edits, new bullet and new paragraph came back as real suggestions that parse back as in sync; a direct edit was pulled into the response. Not yet live-tested: comments (the connector has no way to create one and none were present), tables inserted as suggestions, the optional Subtitle styling. Google's `read_doc` returned no `headingId` for the converted headings, so open items link to the doc with the text to search for, not to the heading.
- **Comments and jump-to-spot (Google Docs):** Claude adds a comment anchored on each open `[DECISION]`, `[OPEN]` and `[EVIDENCE NEEDED]` marker (`rfps-sync-gdoc --comments-plan`, `--comments-commit`; the connector's `update_doc` accepts `insertComment` but has no reply or resolve request). Every comment in the doc, ours and people's, is tracked in `.state/gdoc-comments.json` and `review/doc-comments.md`, with new comments, new replies, resolved and deleted comments reported on each pull, plus two cross-checks against the response (comment still open after its marker left; comment resolved while the marker remains). Open items link to their comment (`?disco=<comment id>`, adjustable with `gdoc_comment_link` in `solution.toml`; the exact link format still needs checking in a browser), else to the doc. `rfps-sync-gdoc --comment-note` records how a comment was handled.
- **Indicators in the Google Doc:** markers are colored by a direct formatting pass (`--highlight-plan`: green GROUNDED, yellow ASSERTION, red DECISION, orange OPEN, purple EVIDENCE NEEDED; formatting only, so not a suggestion per marker). Comments are added for DECISION, OPEN and EVIDENCE NEEDED markers, and also for response changes skipped because the text was edited in the doc (CONFLICT, with the response wording), evidence that is not cleared or missing (EVIDENCE) and banned phrases (BANNED); assertions get none unless `--kinds` asks. A comment follows its marker if the marker is reworded. `--pull --promote` turns a reviewer's open comment into an `[OPEN]` marker (with approval). The pull and `--status` report how many suggestions and comments are waiting for people, and a new flow step, "Suggestions and comments in the shared document settled", tracks them before FINAL. Fixed: a tag followed by punctuation (`[GROUNDED: E-002].`) was not found.
- **Every addition to the Google Doc is a suggestion, including the first draft:** the new doc holds only the template's headings, evaluation lines and placeholders (`--html` is a skeleton), and `--push` always uses `writeMode: SUGGEST`. The `--direct` option and the direct Subtitle styling step are gone.
- `/rfps:pull-docx` is now `/rfps:pull-wip` and handles both routes.
- Shared WIP docx: `/rfps:build-wip` now creates one WIP docx in `05 Draft Response` and updates it in place with `rfps-sync-docx`. Approved response changes go in as tracked changes (author "rfps"), only for paragraphs whose text changed, so other people's comments and edits are kept; a response change that touches text someone edited in the document is reported and left pending. `--status` shows drift, `--dry-run` previews, `--rebuild` regenerates (with a backup). `rfps-build-response --mode wip` remains the stateless regeneration into `build/`.
- `/rfps:pull-wip` (`rfps-sync-docx --pull`): lists edits others made in the shared WIP docx that the response lacks (changed words, new and deleted paragraphs, tables, removed markers) and writes their comments to `review/doc-comments.md`; after approval `--pull --apply` writes them into `response/*.md`, keeping bold and tags on unchanged words. Changes both sides touched are reported as conflicts. The flow's WIP step now shows whether the document or the response is ahead.
- Locators: open items (`open-items.md`, the status page and the pane) link to the shared WIP docx section and show the marker text to search for, once the document exists (`open_in = "docx"|"md"` in `solution.toml` overrides). `rfps-sync-docx` adds an invisible bookmark to every heading, including in existing documents. `rfps-open-doc` opens the document and copies the search text; Word cannot be driven to an exact spot from outside, so use its Navigation Pane for the heading.
- `tools/sync_core.py` plans changes from block texts, separate from the docx backend, so a Google Docs backend can be added later.
- `/rfps:build-final` checks for edits made in the shared document before building.
